# 媒体处理工作区（task schema v4）

浏览器、Android APP、Windows Native 共用任务语义与验证边界。工作区采用“共享入口 → 操作分支 → 共享出口”的结构：源媒体选择、FFprobe/媒体探测和后端能力属于共享入口；硬字幕压制、纯视频转码、视频流复制 / 快速剪辑在中段各自表达不同不变量；成品容器策略、执行、进度、取消、成品验证与保存重新汇合。任务通过经过验证的输出参数数组交给原生后端；输入文件、输出文件及字体路径由后端管理，不能从网页传入任意路径或 shell 命令。

## 使用

1. 选择视频。
2. 在顶部任务选择器中选择硬字幕压制、纯视频转码或视频流复制 / 快速剪辑。
3. 硬字幕模式先完成字幕分析、字体检查及真实 libass 预览；其他模式无需字幕。
4. 硬字幕进入制作阶段后，在“目标控制 / 参数控制”中二选一：
   - 目标控制：继续使用快速预设、目标质量、目标体积和测试片段；
   - 参数控制：打开本工作区，直接设置 codec、preset、CRF/CQ、帧率、尺寸、滤镜、音轨与封装。
5. 参数控制模式先点击“检查设置与执行参数”，再开始处理；目标控制使用其唯一的正式压制入口。
6. 在共享“输出与封装”区域选择 Auto、保持源容器、MKV 或 MP4；不兼容组合会明确失败并要求调整，不会为了容器兼容性静默转码音频。
7. 等待成品验证，点击“保存成品”。

两种硬字幕控制方式共享同一份素材、预检、真实预览和输出验证，同一时刻只显示一个正式执行入口。预设按钮只填入质量和编码速度；分辨率、帧率、裁切等用户设置保持当前值。参数控制任务不运行自动质量校准；需要 SSIM 目标校准时使用“目标控制”。

## 当前开放参数

- 起止时间；视频、音频、软字幕分别选择 `trim/full`。时间轴支持刻度、缩放、波形、源视频刮擦预览。视频 Stream Copy 且视频使用 `trim` 时额外显示关键帧分布、请求 IN 与实际关键帧 IN；源帧预览用于定位，不作为 HDR 色彩判定。
- H.264、HEVC、AV1；Windows 可手动选已通过运行检测的 NVENC 或 CPU 编码器。
- preset、CRF/CQ、目标码率、最大码率、缓冲区。
- 恒定/可变帧率策略；精确分数帧率，例如 `24000/1001`；输出帧数上限。
- 宽高、缩放算法、裁切、旋转、方形像素、去隔行、降噪、去色带、锐化。
- 像素格式、8/10-bit、4:2:0/4:4:4（具体组合由所选编码器验证）。
- GOP、B 帧、参考帧、线程、profile、level、tune。
- NVENC multipass、lookahead、spatial/temporal AQ、AQ strength。
- 有限的 x264/x265/SVT-AV1 专用键值参数；不允许文件路径类参数。参数是否适用于某编码器由该编码器验证，不会悄悄忽略冲突。
- 音频复制/AAC/Opus/关闭；全部音轨或指定音频轨索引；每轨音频码率、声道、采样率。
- 内封软字幕、字体附件、元数据、章节保留开关。
- 成品容器：Auto、保持源容器（可识别且兼容时）、MKV、MP4。视频 Stream Copy 的 Auto 优先保持源容器；其他任务按所选视频/音频组合选择安全容器，无法确认时回退 MKV。

滤镜顺序：裁切 → 去隔行 → 缩放 → 旋转 → 画面滤镜 → 字幕 → 偶数尺寸补边。截取硬字幕视频流会在字幕渲染前恢复原视频时间，渲染后还原输出时间。schema v4 不再全局裁切所有流：只有选择 `trim` 的流使用受 IN/OUT 约束的源输入视图，选择 `full` 的流保持完整。

## 平台与限制

- 成品容器不再固定为 MKV；当前正式支持 MKV 与 MP4。容器是任务字段，不通过改扩展名伪装。schema v4 保留完整视频流集合，可指定单条、多条或全部视频流。
- MP4 使用保守兼容矩阵：当前不会把 Opus、任意软字幕或附件作为 MP4 安全默认，也不会静默改为 AAC；显式不兼容时要求用户改容器或改音频策略。
- 视频流复制 / 快速剪辑只规定所选视频流使用 Stream Copy；音频可独立选择复制、AAC/Opus 转码或关闭。视频、音频、软字幕分别具有 trim/full 时间策略。视频使用 trim + Stream Copy 时由主选视频流重新定位关键帧；仅音频/软字幕剪辑时不得被视频关键帧改变请求起点。
- 浏览器受 1 GiB 输入保护、WebAssembly 及成品 Blob 内存占用约束。
- Android 使用原有 foreground service、SAF/staging、进度、取消及成品导出。当前不默认启用 MediaCodec。
- Windows 明确采用用户所选编码器；失败不会静默替换为另一编码器。
- HDR/高位深源的转码仍受既有保护限制；无损剪切可用。SDR 8-bit 源可请求 10-bit 编码，此操作不会增加源素材已有的信息。
- 指定输出帧数时暂要求关闭音频，以免片长控制歧义。
- 旧章节默认移除；主动保留时应检查剪切后的章节位置。
- 原生后端必须声明 `taskSchemaVersion: 4`，旧 APP/Windows 包会提示更新，避免新设置被旧后端忽略。

## task schema v4：流计划与最终验收标准

v4 不再把“媒体文件”压扁成“一条视频”。媒体探测必须保留完整 stream set，任务必须显式选择视频流。视频流选择使用 FFmpeg video ordinal：`0`、`1`、`0,1` 或 `all`；未选择的视频流不得依赖 FFmpeg 默认行为泄漏进成品。

`operation` 只规定被选视频流的动作：`hardsub`、`transcode`、`copy`。音频策略独立为 `copy / aac / libopus / none`。因此 Video Stream Copy + Audio Transcode、Video Transcode + Audio Stream Copy、Remux + Transcode 都是正式任务语义。

IN/OUT 只定义请求区间；视频、音频、软字幕分别选择 `trim` 或 `full`。实现上，完整流来自 input 0；需要剪辑的流来自受 IN/OUT 约束的 input 1。metadata / chapters / attachments 始终从完整源输入取得。用户故意让视频与音频时长不同是合法状态，软件不得自动把另一类流一起裁掉来“修复同步”。

当前同一任务中，多条被选视频流共享同一种视频操作、编码器和滤镜计划。尚不支持在一个任务里让 `v:0` Stream Copy、同时让 `v:1` 用另一 codec 转码；这属于后续 per-stream heterogeneous action，不会在 v4 中隐式猜测。

为避免伪精确，多视频任务暂不进入 target-size、整片 two-pass 或统一 frames 上限。多视频正式压制也不写入现有单视频 Compression Evidence；单视频 evidence identity 必须包含被选 video ordinal。

### 最终验收矩阵

| ID | 输入 / 操作 | 验收结果 |
| --- | --- | --- |
| V4-01 | 2+ 视频流，指定 `v:1` 转码 | 仅指定视频进入输出，codec/尺寸/流数量与计划一致 |
| V4-02 | 指定 `v:0,v:1` 转码 | 输出包含两条真实转码视频 |
| V4-03 | 指定单条视频压硬字幕 | ASS 只烧入所选输出视频 |
| V4-04 | 指定多条视频压硬字幕 | 所选视频全部经过 libass + encoder |
| V4-05 | 视频 Stream Copy + 音频 AAC/Opus | 视频不经视频编码器，音频按请求转码 |
| V4-06 | MKV→MP4（或反向）+ 视频转码 + 音频复制 | 同一任务真实发生 Remux + Transcode |
| V4-07 | `videoRange=trim` + `audioRange=full` | 视频 packet 对应剪辑区间，音频保持完整 |
| V4-08 | `videoRange=full` + `audioRange=trim` | 视频保持完整，音频 packet 对应剪辑区间 |
| V4-09 | A/V 同时 trim + 视频 Stream Copy | 后端报告实际关键帧切入，不把请求 IN 冒充实际 IN |
| V4-10 | 软字幕 trim/full 与 A/V 独立组合 | 软字幕映射使用正确输入视图 |
| V4-11 | 保留 metadata/chapters/attachments | 非时间资产来自完整源输入；未选视频不进入成品 |
| V4-12 | 只选安全 SDR 流，同时容器另含 HDR 流 | 未选 HDR 不误伤任务；选中未验证 HDR 流则明确拒绝转码 |
| V4-13 | 多视频 + target-size/two-pass/frames | 在语义未定义时提前拒绝，不生成伪精确计划 |
| V4-14 | Web / Windows / Android | producer、capability、parser、执行语义均为 task schema v4 |
| V4-15 | 成品验证 | 按请求验证视频流数量、音轨数量、时长/packet、显式规格和可解码性 |

实际 FFmpeg 集成测试套件定义覆盖 V4-01、02、04、05、06、07、08，并要求对所有产物执行真实解码扫描；是否通过以对应 CI run 为准。Windows CI 另定义 v4 结构化参数验证，Android CI 编译 v4 parser/service。Hosted CI 证据与真实设备证据继续分开。

### 额外约束

- MP4 兼容判断必须覆盖所有被选视频流，而不是只看第一条。
- HDR/高位深保护按被选视频流判断；未选择流不应阻塞任务。
- Stream Copy、Transcode、Remux 是正交维度，UI/报告不得混称。
- 参数编译成功 ≠ FFmpeg 成功 ≠ packet 完整 ≠ 成品可解码 ≠ 目标播放器兼容。

## 体积预算、试压与报告（Web 0.3.0 / Android 0.4.0-native）

码率控制现在分为恒定质量 CRF/CQ、目标平均码率、目标体积。目标体积接受 MB/GB（十进制）和 MiB/GiB（二进制），默认预留 4% 给封装与码率偏差。计算为：

`视频码率 = floor(目标字节数 × (1 − 余量百分比) × 8 / 输出秒数 − 每轨音频码率 × 输出音轨数)`。

- 选择全部音轨时计入每条输出音轨；选择单轨时只计一条。
- 音频复制大小未知时不做可靠体积承诺，需改用 AAC/Opus 的明确码率或关闭音频。
- 目标体积模式拒绝保留未计量附件；软字幕和其他封装开销仍需包含在余量内。
- 不使用 `-fs`；超出预算时完整成品保留，可导出，并提示调整后的视频码率。
- 恒定质量模式不给未经试压的数值估计；试压的外推明确标作片段估计。
- 三组短片使用同一片段，质量值 ±2 或码率 ±20%，显示实际大小、耗时和整片外推；可以保存每个短片并采用其参数。浏览器播放取决于容器/编码支持；原生短片通过现有导出流程保存后观看。
- 自定义配置在本机保存，支持 JSON 导入/导出；不支持的编码器明确提示，不静默替换。预设始终可修改。
- 任务报告 JSON 包含任务参数、实际体积、时长、耗时、预算偏差与重压建议。

x264 的目标平均码率/目标体积模式可启用整片两遍编码，三端均先统计完整所选区间，再编码并带入音频。仅开放已接入验证的 x264 两遍；没有将同一机制套用到 x265、SVT-AV1 或 NVENC。NVENC `multipass` 是逐帧内部分析，与整片两遍不同。

FFmpeg 参数与像素格式通过运行时 help 检查；旧核心缺少 `-fps_mode` 时生成 `-vsync`，也可手动启用兼容选项。NVENC 的 4:2:0 10-bit 请求使用 `p010le`，空间 AQ 和时间 AQ 不能同时启用。音频编码器可用性在执行前检查。v4 原生验证器仍接受旧版 task schema 1–3 用于兼容，但新版 UI 的媒体工作区要求 v4 后端，以保证多视频流选择与独立时间策略不会被旧后端忽略。

输出会核对音视频流数量、时长和 packet 完整性，以及显式指定的帧率、宽高和输出位深。限制总帧数要求明确指定 CFR 目标帧率；短于视频的有效音轨不会仅因提前结束被删除。预算不能保证主观画质，4% 余量也不能保证严格上限。

## 官方资料与研究取舍

- [FFmpeg 主文档](https://ffmpeg.org/ffmpeg.html)：`-fs` 超出限制后停止写入，不适合完整视频的目标体积功能；`-pass` / `-passlogfile` 用于整片两遍统计；`-pix_fmt` 不支持时可能自动回退，因此需要能力与成品检查。
- [NVIDIA FFmpeg 指南](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.1/ffmpeg-with-nvidia-gpu/index.html)：`multipass` 为逐帧内部分析，AQ 与 lookahead 影响感知质量与资源开销。
- [FFmpeg 滤镜文档](https://ffmpeg.org/ffmpeg-filters.html#libvmaf)：VMAF 依赖构建时启用 libvmaf。此次没有给所有平台添加默认 VMAF 分数；各平台核心并不保证包含该依赖，而且硬字幕、缩放、裁切后的评分需要一致的参考处理链路。当前采用真实短片比较，既有字幕预览和字体诊断继续使用。

验证：`node --test src/media-task.test.mjs src/media-planning.test.mjs`；实际 FFmpeg 集成测试新增目标体积、x264 两遍、60 fps、旧帧率参数和 Opus；CI 另验证 Windows 两遍参数与成品规格、Android Kotlin 编译、桌面/手机配置与三片比较交互。

## 纯视频转码：压制前校准曲线（Windows Native）

在“纯视频转码”中打开“压制前 · 实测效率与探索曲线”，选择最低样本 SSIM 和采样力度，然后点击“探索当前编码器”。可使用快速（3 处 × 2 秒）、均衡（5 处 × 4 秒，默认）和深入（7 处 × 6 秒）三档。对于七小时素材，时间位置分散，但这**不是画面复杂度随机抽样**；不能把校准曲线当成整片的置信区间。

搜索在真实选定的 codec/encoder/preset 下测量 CQ/CRF 与实际视频包码率，记录按试验顺序增长的探索轨迹，再拟合局部体积—质量曲线。正式编码路径不受此校准操作影响。选用一个真实测量过的 CQ/CRF 通常比将 CQ 测得的质量曲线换算为目标平均码率更具有可比性。沿曲线采用码率时，界面会明确提示无法保证相同 SSIM 或最终大小。

SSIM 是局部客观指标，不能保证 4K60 运动细节的主观质量；短片码率离散度会展示在读数中。复制源音频时无法可靠估计其字节预算；若音频保持完整而视频只裁切部分，程序会按对应音轨时长调整预算。平台目前限定 Windows Native，且当前校准只覆盖原尺寸/帧率、SDR 8-bit 4:2:0、无额外视频滤镜、主视频流 v:0 与默认高级参数。未能等价测量的参数组合会拒绝校准而不是提供伪精确曲线。

“停止探索”在当前原生短片试压完成后中断，并清除不完整证据；不是立即杀死正在运行的 FFmpeg 进程。源素材、编码器、preset、时间区间或采样档位改变后会作废旧结果。对长时长母片，先用快速档判断可行性，再用均衡/深入档复核，同时务必检查复杂运动场景。

校准准备和采样等待期间改变素材或参数，也会停止后续探索并作废结果；修改 SSIM 目标时立即生效，无需先离开输入框。采用质量值或码率前会再次核对当前素材和方案，其他处理任务运行期间不能采用校准参数。

Windows Native 的无字幕精确采样使用**直接解码源片参与 SSIM**，不再为每一个候选参数写出 4K60 FFV1 临时参考视频。硬字幕试压仍保留真实 libass 渲染后的 FFV1 参考。新路径以同一视频时间区间重新归零时间戳进行比较，并在测试中检查 seek 后帧对齐；实机仍需复验色彩、HDR 与变帧率等素材边界。

## 曲线的图形语义

探索图的横轴是**搜索轮次**，虚线只连接实际试压顺序，并非连续可预测的 CQ 函数；圆点周围的细竖线展示同一参数在分散采样场景中的 SSIM 范围，水平虚线是所设定的最低样本 SSIM 阈值。效率图的横轴是对数比例的**目标预算体积（GB）**，纵轴是 SSIM；空心实测点与连续局部拟合线明确分离，半透明区域是短片离散范围、不是置信区间。菱形标注局部效率拐点，仅供比较，不自动保证推荐最优。

两个入口均使用同一份绘图与指针坐标变换。选择点时可用拖动、方向键和 Home/End；滑动到测试范围边界时停止外推。在纯转码页，原音频直接复制时仍须记得体积横轴**未计入音频字节**，不是最终输出体积保证。
